A low-code tool for developers: composing internal applications in VS Code with Python

Product designer: Victoria Molgado

User research ✢ Design system ✢ User interface

Context

In search of product-market fit, Abstra was exploring the thesis of adoption through offering a faster and more intuitive way for developers (or technical users) to build complex internal tools.

The strategy was product-led growth: developers adopt the tool, making it easier to sell it to their companies later.

Problem

Those tools carry complex interactions and weigh heavily on companies’ productivity. Developers often build them without dedicated design support. Abstra could take on the complexity of design decisions through a system that already accounted for layout, styling, and interaction states.

Scope

We picked a VS Code plugin for composing interfaces from ready-made widgets, connecting them to business rules in Python, and deploying internal tools within the developer’s coding workflow.

The VS Code plugin was chosen as the medium to meet users where they already were, reducing context switching between IDEs, the terminal, and the browser.

The visual builder had to reduce interface work without limiting how engineers wrote business logic.

The design challenge was to define where to give developers control and where the system should make a decision for them.

Foundation

The design system was the widgets’ main specification. It had to define how components behaved together, so developers could assemble a complex tool without designing every interaction themselves.

Foundation: Positioning

Placement was one of those decisions. So I decided to compartmentalize: the grid is how we set positioning. Users could place components inside 12 columns, and their height would meet a strict rectangular-blocks system that ensured different heights would still keep alignment.

This separated choosing where a widget belonged from adjusting the space inside it.

Foundation: Spacing

While the grid was only responsible for placement, components were responsible for padding (the space between components). All of them had an 8px internal margin; that made sure they’d connect well enough when placed near, and would not be associated when placed into different columns.

The component decisions introduced one of the biggest visual tradeoffs of this project. In some situations, it introduced uncomfortable column spacing between content blocks. But because our goal was to validate product-market fit, I decided to leave it as a future improvement.

Components behavior

Components were flexible in their purpose and restrained in their styling. The system aimed to make Abstra recognizable through consistent composition while leaving room for the client’s brand. For the original builder, interviews with the implemented version were used to look for blind spots and inform revisions.

Behavior highlights — Sidebar and navigation control

Containers needed their own rules. A sidebar could act as a canvas, but it did not have the same purpose or room as the main workspace. Later interaction specifications made that boundary explicit: a smaller set of components could be dropped into a sidebar, while modals had three canvas sizes. Reusing the composition model still required defining what each container could accept.

Those specifications also separated editing from testing. In editing, selecting a widget would expose its properties in the Inspector, with changes reflected on the canvas. In testing, the canvas would respond as the finished tool, with a way back to editing. The same click needed a clear meaning in each mode: configure the component or use it.

Color and Themes

Developers could bring their brand without having to assemble and maintain a palette themselves. A single hexadecimal value was enough to define a brand color — on light or dark interfaces.

The palette derived from that color had to work across surfaces and states. The later theme specification kept light and dark surfaces fixed and required the generated colors to preserve contrast with backgrounds and labels.

Widget states were part of the same responsibility. The later interaction specifications covered button hover and click states, text-input selection, errors and clearing, and corresponding selector behavior. A clean default appearance was only useful if the component remained understandable when someone interacted with it.

Interfaces composed with Abstra's VS Code Plugin
Outcome

We launched on Product Hunt and VS Code and the plugin recorded 7,000 downloads on its first day. A YouTube overview spread organically, and VS Code featured Abstra on the Marketplace homepage for two weeks.

Although we had a strong point of view, I conducted user interviews and user testing while designing the interactions.

The design addressed the interaction part, the effort of building an internal interface. The business team now had a working tool to demonstrate on sales calls, and a consistent and high-quality answer to “how does it work?”
